# B200 迁移与启动手册

从零到跑起 auto-scaffold 训练的完整步骤。所有脚本零硬编码路径:机器差异全部通过
环境变量 / 命令行参数表达,同一套命令在任何 CUDA ≥ 12.8 的机器上成立。

已知版本基准(2026-08-11 在 H100 机器上完成 10 周期无人值守烟测的组合,cu128 wheel
与 triton 3.4 原生支持 Blackwell sm_100):

| 组件 | 版本 |
|---|---|
| torch | 2.8.0+cu128 |
| vllm | 0.11.0 |
| triton | 3.4.0(随 vllm) |
| ray | 2.52.1 |
| transformers | 4.56.1 |
| CUDA toolkit | ≥ 12.8(nvcc 编译生成内核用) |

## 1. 上传

源机器上(repo 干净、已推送 GitHub 时用 git 模式;否则 rsync 模式直接拷工作树):

```bash
# 仓库 + 两个模型一起送过去
scripts/sync_to_remote.sh user@b200-host \
  --models "/path/to/drkernel-8b-coldstart-eosfix /path/to/Qwen3-8B" \
  --remote-root '~/autoscaffold'

# 远端无法访问 GitHub 时:
scripts/sync_to_remote.sh user@b200-host --repo-mode rsync --models "..."
```

模型也可以在远端直接拉(需要 HF_TOKEN,base 模型是私有仓库):

```bash
hf download Mingyi-Hong/drkernel-8b-coldstart-eosfix --local-dir "$ROOT/models/drkernel-8b"
hf download Qwen/Qwen3-8B --local-dir "$ROOT/models/Qwen3-8B"
```

## 2. 环境(B200 机器上,与 ALFWorld 迁移相同的 uv 打包方式)

```bash
cd ~/autoscaffold/repo
bash scripts/setup_b200_uv.sh           # 一条命令:uv 自带 Python 3.12,按 357 包精确冻结安装
```

细节:安装集来自 `requirements-b200-freeze.txt`(H100 上跑完整夜烟测的环境逐包冻结);
flash_attn 自动从官方 release 拉预编译 wheel(离线机器用 `FLASH_ATTN_WHEEL=` 指本地文件);
sm_100+ 上自动剔除 flashinfer(其预编译 wheel 在 B200 上使 vLLM 起不来,ALFWorld 迁移时
踩过)。机器没装 uv 也不用管,脚本会装。根盘小就设 `VENV_DIR=` 和 `UV_CACHE_DIR=` 指向
大盘。不用 uv 的话 `scripts/setup_b200_env.sh` 是等价的 pip 版本。

## 3. 体检

```bash
export ARM_PYTHON=~/autoscaffold/repo/.venv/bin/python
export ARM_MODEL=~/autoscaffold/models/drkernel-8b-coldstart-eosfix
export JUDGE_MODEL=~/autoscaffold/models/Qwen3-8B
export AUTOSCAFFOLD_OPENAI_KEY_FILE=~/autoscaffold/openai.key   # 文件内容:OPENAI_API_KEY=sk-...
bash scripts/b200_preflight.sh
```

全绿再继续。逐项检查的都是曾经让运行静默出错或卡死的东西:驱动/算力、nvcc 版本对
sm_100 的支持、torch/vllm/ray/openai 可导入、flashinfer、数据 parquet、模型目录、
Teacher 凭据、/dev/shm 容量。

## 4. 启动

```bash
# 判官先起(独占一张卡,端口 8210)
bash scripts/serve_rubric_judge.sh --model "$JUDGE_MODEL" --gpu 7 &

# 写一份 env 文件,作为该实验的唯一配置来源(watchdog 也读它)
cat > ~/autoscaffold/run1/env.sh <<'EOF'
export ARM_ROOT=$HOME/autoscaffold/repo
export ARM_PYTHON=$HOME/autoscaffold/repo/.venv/bin/python
export ARM_CUDA_HOME=/usr/local/cuda-12.9
export ARM_MODEL=$HOME/autoscaffold/models/drkernel-8b-coldstart-eosfix
export JUDGE_MODEL=$HOME/autoscaffold/models/Qwen3-8B
export ARM_DOMAIN=triton
export ARM_EXP=b200_run1
export ARM_EXP_ROOT=$HOME/autoscaffold/run1/exp
export ARM_CKPT_ROOT=$HOME/autoscaffold/run1/ckpts     # 放大盘;每份 checkpoint ~36G,保留 2 份
export ARM_GPUS=0,1
export ARM_REWARD_GPU=3
export ARM_TARGET_STEP=200
export AUTOSCAFFOLD_OPENAI_KEY_FILE=$HOME/autoscaffold/openai.key
# 不要设 ARM_TORCH_CUDA_ARCH_LIST —— 留空即自动探测(B200 = 10.0);只有交叉编译才需要设
EOF

# 启动训练(前台首启建议先跑 1 个 cycle 验证,再换 100)
source ~/autoscaffold/run1/env.sh
bash scripts/launch_autoscaffold.sh 100 >> ~/autoscaffold/run1/run.log 2>&1 &

# 看护(5 分钟一巡:拉活训练/判官、D 态熔断、磁盘守卫、孤儿 checkpoint 清理、崩溃环刹车)
nohup "$ARM_PYTHON" scripts/watchdog.py --env-file ~/autoscaffold/run1/env.sh \
      --judge-gpu 7 >/dev/null 2>&1 &
```

launch 脚本启动前自带安全门:先用 4 秒验证 kernel_runner 的跨进程并发上限真实生效
(该上限失效曾两次拖垮共享节点),再检查 D 态进程数,任一不过即拒绝启动。

## 5. 运行中看什么

- `run.log`:`[cN] train rollouts ...` / `[cN] step=… valid_seen …` / `[cN] teacher: …` /
  `[cN] A/B: … -> ACCEPT/reject` 是每周期的四条主线日志。
- `exp/<EXP>/state.json`:step、sr_history、best、完整 decision_history。
- `watchdog.log`:每 5 分钟一行 `ok arm=up step=…`;出现 `CRASH-LOOP`/`D-STATE`/
  `DISK LOW` 即需人工介入,HALT 文件存在时 watchdog 不再拉起任何东西
  (处理完 `rm HALT` 即恢复)。

## 6. 与 H100 烟测的已知差异点

- 目标 GPU 描述:Teacher 的域事实现在从驱动探测(`ARM_GPU_DESC` 可覆盖),B200 上会
  自动写成 Blackwell/sm_100。
- `TORCH_CUDA_ARCH_LIST`:三层(训练、评测、判官子进程)全部自动探测,链路上没有
  任何 sm_90 残留;`ARM_TORCH_CUDA_ARCH_LIST` 仍可强制覆盖。
- 磁盘:checkpoint 保留数上限 2(`max_ckpt_keep` 可在 cfg 覆盖),扩展构建缓存在
  /dev/shm,watchdog 兜底清理 —— 烟测夜里根盘两次写满的事故路径均已封死。
- 正式实验建议 `ARM_VAL_N≥3`(单 draw 噪声 ±0.033,烟测里多次误读趋势)。
